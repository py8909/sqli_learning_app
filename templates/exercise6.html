演習6：脆弱なコードを静的解析で見つけてみよう
難易度：★★★（上級） 対象：Python / Flask コード
1. 演習の目的
これまでの演習では、実際にフォームやURLから攻撃を行いました。 この演習では視点を変え、「ソースコードを読んで脆弱箇所を見つける」 静的解析を体験します。

実際の開発現場では、コードレビューや静的解析ツールが SQLインジェクション対策の重要な役割を担っています。
2. 対象となる脆弱なコード
例として、次のような Flask アプリの一部を考えます： 
@app.route("/search")
def search():
    q = request.args.get("q", "")
    query = "SELECT * FROM items WHERE name LIKE '%" + q + "%'"
    cursor.execute(query)
    rows = cursor.fetchall()
    return render_template("search.html", rows=rows, q=q)
このコードのどこが問題か、自分の目で確認してみましょう。
3. やってみよう
右側の「脆弱コード」欄を読み、以下の観点から危険な行を探してみてください：
  • ユーザ入力（request.args / request.form）はどこか
  • その値はどのようにSQL文へ渡されているか
  • 文字列連結は行われていないか
  • パラメータバインド（プレースホルダ）は使われているか
ヒントを見る（クリックで展開）
＋

● SQLインジェクション観点で見るべきポイント

  • ・request.args.get / request.form.get から取得した値
  • ・"... " + 変数 + " ..." のような文字列連結
  • ・cursor.execute(...) に直接埋め込まれているか
  • ・WHERE や LIKE の条件にユーザ入力を入れていないか

これらがそろっている場合、静的解析ツールは「SQLインジェクションの疑いあり」と判定できます。

4. 学習のポイント
  • ・静的解析では「データの流れ（データフロー）」を見る
  • ・入力元（ソース）→ SQL実行箇所（シンク）を追跡する
  • ・プレースホルダを使えば、静的解析でも「安全な書き方」と判断しやすい
  • ・自動ツールと人間のレビューを組み合わせることが重要
5. SQLインジェクションを防ぐための方法（対策）
静的解析の目的は「危険な書き方を早期に排除すること」です。SQLi対策は、実装面だけでなく 開発プロセス（レビュー/ツール/運用）も含めて設計します。
  • パラメータ化クエリ（Prepared Statement）/ ORMを標準にする（文字列連結禁止）
  • 入力検証（バリデーション）で不正な形式や長すぎる入力を排除する
  • 最小権限：アプリ用DBユーザに DROP/ALTER 等の権限を与えない
  • エラー情報の抑制：本番でスタックトレースやSQL詳細を表示しない
  • レビュー + 静的解析ツールをCIに組み込み、危険パターンを自動検出する
6. 安全な実装例（Prepared Statement / ORM）
# 悪い例（文字列連結：SQL構造が壊れうる）
query = "SELECT * FROM users WHERE username = '" + username + "'"
cursor.execute(query)

# 良い例①（プレースホルダ：DB-API）
cursor.execute(
    "SELECT * FROM users WHERE username = ? AND password = ?",
    (username, password)
)

# 良い例②（SQLAlchemy ORMの例：値がバインドされる）
user = User.query.filter_by(username=username).first()
# ※ パスワードはハッシュ照合（DBで平文比較しない）
7. 静的解析で見るべき「危険パターン」チェックリスト
静的解析（人のレビュー含む）では、次の組み合わせを重点的に探します。
  • ソース（入力）：request.args, request.form, JSON, Cookie など
  • 加工（危険）："..." + var, f-string, format() でSQLを組み立てる
  • シンク（実行）：cursor.execute(), db.execute(), ORMのraw SQL実行
「入力 → 文字列連結 → SQL実行」が揃っていれば、SQLiの疑いが高いと判断できます。
8. まとめ
SQLi対策は「入力を消毒する」よりも、SQLと値を分離（パラメータ化）することが本質です。 静的解析は、そのルールをコード全体に適用できているかを確認する強力な手段になります。
