演習5：ブラインド SQLインジェクション攻撃を体験しよう
難易度：★★★（上級） 対象：True/False・レスポンス長・時間差
1. 演習の目的
ブラインドSQLインジェクションは、 画面にエラーも結果も表示されない場合でも成立する攻撃 です。 この演習では以下3種類のBlind SQLiを体験します：
  • ① True/False ベース
  • ② レスポンス長ベース
  • ③ 時間差（Time-based）ベース
2. 想定される脆弱な実装
ブラインドSQLiは、次のような「結果を画面に返さないAPI」で起こります： 
q = request.args.get("q", "")
query = "SELECT * FROM users WHERE name = '" + q + "'"
rows = cursor.fetchall()
return "OK"
「OK」しか返さないため、 攻撃者は応答内容（または時間）から成功を推測します。
3. やってみよう
右側フォームに以下を入力して試してみてください：
  • ① True/False： ' OR 1=1 --
  • ② False： ' AND 1=0 --
  • ③ 時間差： ' OR sleep(3) --（DBによって関数名が異なる）
  • ④ レスポンス長： ' UNION SELECT 'AAAAA...' --
応答の 速度・長さ・挙動の違い を観察しましょう。

Blind SQLi のポイント

  • 画面に結果が表示されなくても攻撃は成立する
  • True/Falseで応答の違いを見ることで内部情報を推測する
  • 時間差は強力で、1文字ずつ抽出が可能
  • 脆弱APIは「情報の非表示＝安全」と誤解しがち

ブラインドSQLiは自動化しやすいため、 実際の攻撃で最も利用される危険な手法です。

4. 学習のポイント
  • 画面に情報が出ないから安全という考えは間違い
  • 応答時間や内容の微妙な差で内部情報を推測可能
  • Prepared Statement / ORM を使うと防御できる
  • ログ監視・レート制限も重要な対策となる
5. SQLインジェクションを防ぐための方法（対策）
ブラインドSQLiは「結果を見せない」だけでは防げません。防御の本質は、 SQL構造とユーザ入力を分離することと、 推測に使える“差”を作らない運用です。
  • パラメータ化クエリ（Prepared Statement）/ ORMを必須にする（文字列連結禁止）
  • 例外メッセージを外部へ返さない（本番でスタックトレース/詳細を隠す）
  • レスポンスの統一：成功/失敗で本文やサイズの差を過度に出さない（可能なら一定化）
  • 時間差の抑制：極端な処理時間の差を出さない、DB関数の利用を制限する
  • レート制限・WAF・検知：繰り返し試行（自動化）を止める、ログで検知する
  • 最小権限：アプリ用DBユーザに不要な権限（DDL/拡張機能など）を付与しない
6. 安全な実装例（Prepared Statement / ORM）
# 悪い例（SQLを文字列連結で構築）
query = "SELECT * FROM users WHERE name = '" + q + "'"
cursor.execute(query)

# 良い例①（DB-API：プレースホルダ）
cursor.execute("SELECT * FROM users WHERE name = ?", (q,))

# 良い例②（SQLAlchemy ORM：値はバインドされる）
rows = User.query.filter(User.name == q).all()
7. Blind 対策の追加ポイント（設計・運用）
  • 一定時間以上のクエリを遮断/監視（DB側タイムアウト、アプリ側サーキットブレーカ）
  • 一定回数の失敗でブロック（IP/アカウントごとの制限）
  • 監査ログ：OR 1=1 / UNION / sleep の試行を記録
ブラインドSQLiは「自動化」が前提になりやすいため、 レート制限と検知は実務上非常に有効です。
