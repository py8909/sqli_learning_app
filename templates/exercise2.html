演習2：検索フォームでSQLインジェクション攻撃を体験しよう
難易度：★★☆（中級） 対象：検索機能
1. 演習の目的
検索フォームに対して SQL インジェクション攻撃を行い、 データ漏洩・UNION攻撃・構文エラー の危険性を理解します。
2. 想定される脆弱な実装
query = "SELECT * FROM items WHERE name LIKE '%" + q + "%'"
cursor.execute(query)
3. やってみよう
  • ① 普通の検索をする
  • ② クォート ' を入力する
  • ③ ' OR '1'='1 を入れる
  • ④ ' UNION SELECT ... -- を試す

この脆弱な検索処理では、UNION攻撃・Error-based・Blind SQLi などが成立します。

＋

試せる例：

  • '
  • ' OR '1'='1
  • ' UNION SELECT name, sql FROM sqlite_master --

このフォームでは検索結果に SQLiの結果がそのまま表示される ため、攻撃が成立したかを観察できます。

4. 学習のポイント
  • 検索フォームは攻撃者に最も狙われやすい機能
  • UNION攻撃により内部テーブルが漏洩する危険
  • LIKE句でも文字列連結は危険
  • Prepared Statement を使うと安全になる理由を理解する
5. SQLインジェクションを防ぐための方法（対策）
検索フォームは外部入力をそのまま検索条件に使うため、SQLiの標的になりやすい機能です。 対策の基本は 「入力値をSQL文字列に連結しない」 ことであり、特に次の点が重要です。
  • プレースホルダ（Prepared Statement / パラメータ化クエリ）でSQL構造と値を分離する
  • LIKE句のワイルドカード（% / _）の扱いを意識し、必要に応じてエスケープする
  • エラーメッセージを画面に出さない（構文エラーから内部構造が推測される）
  • 表示データの最小化（検索結果に機密情報・内部テーブル情報を含めない）
  • 最小権限の原則（検索用アカウントに不要な権限を与えない）
6. 安全な実装例（LIKE検索のパラメータ化）
            -- 悪い例（文字列連結：q がSQL構造を壊せる）
            SELECT * FROM products WHERE name LIKE '%${q}%';

            -- 良い例（パラメータ化：値はSQLとして解釈されない）
            SELECT * FROM products WHERE name LIKE ?;

            # Python例（DB-APIのプレースホルダを利用）
            pattern = "%" + q + "%"
            cursor.execute(
            "SELECT * FROM products WHERE name LIKE ?",
            (pattern,)
            )
7. 追加の注意（UNION・内部情報漏洩を防ぐ）
UNION攻撃は「検索結果として本来想定していない列」を表示できてしまう点が危険です。 そのため、SQLi対策に加えて次の設計も有効です。
  • 検索結果のSQLは SELECT 列を明示し、不要な列（パスワード、管理フラグ等）を返さない
  • DBエラーはユーザーに返さず、サーバ側ログのみに記録する
  • 検索APIに レート制限を入れ、Blind SQLiの総当たりを難しくする
8. 演習のまとめ
この演習では、検索条件にユーザー入力を連結すると、LIKE句でもSQL構造が改変され得ることを確認します。 対策の要点は、パラメータ化クエリを徹底し、加えてエラー抑制・最小権限・返却データの最小化を組み合わせることです。
