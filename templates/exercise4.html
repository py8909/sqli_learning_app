演習4：エラーベース SQLインジェクション攻撃を体験しよう
難易度：★☆☆（初級） 対象：構文エラー／カラム数エラー
1. 演習の目的
SQLのエラーメッセージを利用して内部情報を引き出す エラーベース SQLインジェクション を体験します。
2. 想定される脆弱な実装
q = request.args.get("q", "")
query = "SELECT * FROM items WHERE name LIKE '%" + q + "%'"
cursor.execute(query)
3. やってみよう
以下を試してみましょう：
  • '（構文エラー）
  • ' OR '1'='1
  • ' UNION SELECT 1 --
  • ' UNION SELECT name, sql FROM sqlite_master --
ヒントを見る（クリックで展開）
＋

● エラーは攻撃者への“メッセージ”になる

  • 構文エラー → クォートの有無がわかる
  • カラム数エラー → UNION の列数が推測できる
  • UNIONエラー → UNION攻撃が使えるか判別
4. 学習のポイント
  • ・エラーメッセージは攻撃者に情報を与える
  • ・安全なアプリは内部エラーを露出しない
  • ・Prepared Statement がエラー防御にも有効
5. SQLインジェクションを防ぐための方法（対策）
エラーベースSQLiが成立する大きな要因は、ユーザー入力がSQL文に連結されることに加えて、 DBの詳細エラーがそのまま画面に露出することです。対策は次の3点が中核になります。
  • パラメータ化クエリ（Prepared Statement）でSQL構造と値を分離し、文字列連結をやめる
  • 詳細エラーメッセージをユーザーに返さない（共通エラーページ + サーバ側ログ）
  • 最小権限の原則で、仮にSQLiが起きても被害を抑える
6. 安全な実装例（パラメータ化 + 例外処理）
            -- 悪い例（文字列連結：構文エラーやUNIONエラーが情報源になる）
            query = "SELECT * FROM items WHERE name LIKE '%" + q + "%'"
            cursor.execute(query)

            -- 良い例（パラメータ化：入力がSQLとして解釈されない）
            pattern = "%" + q + "%"
            cursor.execute("SELECT * FROM items WHERE name LIKE ?", (pattern,))

            -- 良い例（例外処理：詳細エラーは画面に出さずログへ）
            try:
                cursor.execute("SELECT * FROM items WHERE name LIKE ?", (pattern,))
            except Exception as e:
                logger.exception("DB error")   # サーバ側ログに記録
                return "Internal Server Error" # 画面には一般的なメッセージのみ
7. エラーベース攻撃を成立させない設計のポイント
エラーベースSQLiでは、攻撃者はエラー内容から 「クォートの有無」「列数」「DB種別」「テーブル名」などを推測します。 そのため、次の設計が特に有効です。
  • 本番ではDEBUGを無効化し、スタックトレースを表示しない
  • 共通エラーハンドラを用意し、DB由来の例外を一律でマスクする
  • SELECT * を避け、返す列を明示して想定外データの露出を抑える
  • 入力のバリデーション（長さ・文字種の制限）で攻撃文字列を通しにくくする
8. 演習のまとめ
この演習では、SQLのエラーが「攻撃者へのヒント」になり、UNIONの列数推測や内部情報の特定につながることを学びます。 対策の要点は、パラメータ化を徹底した上で、詳細エラーを利用者に返さない設計にすることです。
