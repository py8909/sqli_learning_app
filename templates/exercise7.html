演習7：動的解析デモ（SQLi自動検出）
難易度：★★★★（上級） 対象：レスポンス差分・HTTPステータス
1. 演習の目的
動的解析は、攻撃ペイロードを実際に送信し、 レスポンスの変化から SQLインジェクションを検出する手法です。

この演習では、次の点を体験します：
  • 正常時（ベースライン）との差分を見る
  • ステータスコードの変化を見る
  • レスポンス長の増減を見る
  • エラーメッセージの露出を見る
2. 動的解析の仕組み
典型的なSQLi検出ロジックは次の通りです：
  • ベースライン取得：正常な入力を送信し、レスポンスの状態を記録
  • 攻撃ペイロード送信：SQLi攻撃を試みるペイロードを送信
  • 差分解析：ステータスコード、長さ、内容を比較
  • 判定：差分が一定基準を超えた場合、SQLiの可能性ありと判断
3. やってみよう
右側のフォームから攻撃ペイロードを送信し、動的解析結果を確認しましょう。
  • ' OR '1'='1 --
  • ' UNION SELECT 1,2,3 --
  • '; DROP TABLE users; --
ヒントを見る（クリックで展開）
＋

動的解析が利用する主な指標：

  • ステータスコード：200 → 500 になった？
  • レスポンス長：急に長くなった？短くなった？
  • エラーメッセージ：DBの構文エラーが露出している？

これらが起きたら、SQLiの可能性が高いと判断できます。

4. 学習ポイント
  • 動的解析はアプリの「振る舞い」を観察する手法
  • 静的解析と組み合わせると精度が向上する
  • 実際の診断ツールも差分解析（ベースライン比較）を使う
  • Time-based / Blind SQLi の検出にも応用可能
5. SQLインジェクションを防ぐための方法（対策）
動的解析は「検出」であり、対策（防御）は「作り方」で決まります。 実装・運用の観点では以下が基本です：
  • パラメータ化クエリ（Prepared Statement）/ ORM を必須化（文字列連結でSQLを作らない）
  • 入力検証：型・長さ・許可文字を制限（ただし“入力検証だけ”では防げない）
  • エラーの秘匿：DB/SQL詳細を画面に出さない（本番は共通エラーページ）
  • 最小権限：アプリ用DBユーザに不要な権限（DROP/CREATE等）を持たせない
  • 監視・制限：WAF、レート制限、異常ペイロードのログ/検知（自動攻撃に効く）
6. 安全な実装例（Prepared Statement / ORM）
# 悪い例（SQLを文字列連結で構築）
query = "SELECT * FROM users WHERE name = '" + q + "'"
cursor.execute(query)

# 良い例①（DB-API：プレースホルダ）
cursor.execute("SELECT * FROM users WHERE name = ?", (q,))

# 良い例②（SQLAlchemy ORM：値はバインドされる）
rows = User.query.filter(User.name == q).all()
7. 動的解析を活かした“守り”の考え方
動的解析の結果は、次の改善に直結させると効果的です：
  • 検出したパラメータ箇所を最優先でパラメータ化/ORM化
  • 差分が出る原因（エラー露出、レスポンス肥大）を共通化・秘匿
  • “同じ攻撃が繰り返せる”場合はレート制限・遮断ルールを追加
